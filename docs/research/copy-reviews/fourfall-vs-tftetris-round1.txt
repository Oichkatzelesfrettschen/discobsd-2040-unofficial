FOURFALL CLEAN-ROOM COPYING REVIEW
==================================

VERDICT: NEEDS CHANGES

The normalized-source score passes the specified 5 percent rejection gate, and
the legacy identifiers, comments, device paths, drawing code, collision API,
line-clear algorithm, and bag algorithm are absent. Three base-shape rows use
the same behaviorally irrelevant cell order as legacy coordinate rows, however.
The specification says that a candidate which matches legacy coordinate lists
in line order fails the table audit. The new palette also assigns six shapes the
same colors as the legacy program. Shape geometry is a public mechanic; cell
order and the shape-to-color permutation are expressive choices. The source,
vectors, specification, tests, and implementation record should change together
before this review returns a clean verdict.

Findings that require changes
-----------------------------

F1 -- expressive per-piece palette and trade-dress risk

New: games/fourfall/fourfall.c:617-618
Original: legacy/non-arm/mips-pic32/share/examples/gpanel/tftetris.c:315
Related new assertions: games/fourfall/tests/play.py:302,305,309,312,315,318,323
Classification: EXPRESSIVE. Choosing seven shapes is forced by the public
mechanic. Assigning cyan to I, yellow to O, magenta to T, green to S, red to Z,
and blue to J is a selectable visual mapping. Those six semantic assignments
match the original. Fourfall assigns white to L where the original assigns
orange. The console constraint supplies seven nonblack basic colors, but it
does not force their 7-factorial shape permutation. The same mapping therefore
creates the strongest trade-dress similarity in the reviewed implementation.
Suggested rewrite: choose a distinct permutation, for example I white, O blue,
T green, S magenta, Z cyan, J red, and L yellow. Update the implementer
specification, ff_color, the pty color assertions, and the implementation record
as one change. Preserve monochrome mode as an independent presentation.

F2 -- O base row repeats a legacy coordinate row in the same order

New: games/fourfall/fourfall.c:99 and games/fourfall/tests/vectors.txt:5-8
Original: legacy/non-arm/mips-pic32/share/examples/gpanel/tftetris.c:272
Classification: FORCED GEOMETRY, EXPRESSIVE ORDER. The square cell set is the
public O shape, and row-major order is conventional. Collision and drawing do
not depend on the order of the four cells, so the particular sequence
{0,0},{0,1},{1,0},{1,1} remains selectable. The checklist expressly rejects a
legacy coordinate list that matches in line order.
Suggested rewrite: use a consistent non-legacy cell enumeration, such as
reverse row-major order, for every base shape. Regenerate all four O SHAPE
vectors and any test oracle that treats cell order as significant.

F3 -- Z base row repeats a legacy S-orientation row in the same order

New: games/fourfall/fourfall.c:102 and games/fourfall/tests/vectors.txt:17
Original: legacy/non-arm/mips-pic32/share/examples/gpanel/tftetris.c:278
Classification: FORCED GEOMETRY, EXPRESSIVE ORDER. Fourfall interprets pairs as
(row,col), while the original interprets pairs as (x,y), and the type labels
differ. Those facts make the geometric interpretation different, but the raw
ordered list {0,0},{0,1},{1,1},{1,2} still matches. Cell enumeration is not a
game rule.
Suggested rewrite: reorder the four Z base cells under the same global
enumeration rule used for F2, then regenerate the four Z SHAPE vectors.

F4 -- J base row repeats a legacy L-orientation row in the same order

New: games/fourfall/fourfall.c:103 and games/fourfall/tests/vectors.txt:21
Original: legacy/non-arm/mips-pic32/share/examples/gpanel/tftetris.c:258
Classification: FORCED GEOMETRY, EXPRESSIVE ORDER. Axis meaning and type label
differ, but the raw ordered list {0,0},{1,0},{1,1},{1,2} matches. The public
four-cell shape does not force the iteration order.
Suggested rewrite: reorder the four J base cells under the same global
enumeration rule used for F2, then regenerate the four J SHAPE vectors.

F9 -- collision loop shares only the public mechanic and a return idiom

Classification: FORCED MECHANIC AND C IDIOM. Both implementations inspect four

F10 -- public screen concepts use a different rendering system

Original: legacy/non-arm/mips-pic32/share/examples/gpanel/tftetris.c:393-450,

Classification: FORCED MECHANIC WITH DISTINCT EXPRESSION. Both games display a

Suggested rewrite: retain the rendering architecture. Apply the distinct palette

Commercial name and trade-dress check
-------------------------------------

A case-insensitive whole-word byte search finds the commercial game name in
neither games/fourfall nor docs/research/fourfall-implementation.md. The search
includes source, tests, the existing test ELF, and Python bytecode. The
implementation record names the legacy filename tftetris.c at lines 7 and 260;
the filename serves provenance and does not present the commercial name as the
new game's name. The reviewer specification itself necessarily names the term
in its prohibition and reviewer-only checklist; those references are review
evidence rather than Fourfall branding.

Fourfall uses the title FOURFALL, an ASCII terminal frame, a left-side board,
a right-side text panel, and no logo, music, legacy prompt, legacy URL, bitmap
font, gradient, or pixel-block drawing. Those measured surfaces differ from the
original. F1 prevents a clean trade-dress result because the shape-to-color
mapping remains a selectable visual choice with six semantic matches. F6
records the generic end-state wording as a lower-risk presentational overlap.

Residual uncertainty
--------------------

The review establishes the measured digest, fixed-string results, normalized
16-token overlap, table coincidences, listed algorithm differences, and the
observed name/presentation surfaces. The review does not establish that genre

the manual algorithm pass addresses only the fingerprints named by the supplied
