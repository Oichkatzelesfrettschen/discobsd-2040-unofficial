# Native C Compilers for On-Device Compilation on DiscoBSD/RP2040

## 1. The constraint

DiscoBSD runs on an RP2040 (ARM Cortex-M0+, ARMv6-M, Thumb-1 instruction set only, no hardware integer divide, no MMU), and each user process gets at most 96 KB of RAM for text, data, and stack combined (MAXMEM). A native, on-device C compiler must therefore run its own parsing, code generation, and any intermediate data structures inside a process that also has to hold its own code and data -- realistically well under 96 KB of live heap plus stack at peak, not just at rest. Root filesystem flash is scarce too: about 340 KB free after a minimal install, or up to about 720 KB if the kernel region is shrunk, so the installed compiler binary (plus its cpp, assembler front end if any, and libc) has to fit that budget as well. The system already carries a native toolchain inherited from the RetroBSD/DiscoBSD lineage (`usr/bin/cc`/`ccom`/`cpp`/`as`/`ld`), plus `smlrc`, `picoc`, and `lcc`/`lccom`/`lcpp`, so this report evaluates whether any of those, or an outside candidate, is the best fit for a real ARMv6-M/Thumb-1 on-device compiler, and at what cost to port one that is not there yet. DiscoBSD's active fork lives at [github.com/chettrick/discobsd](https://github.com/chettrick/discobsd).

## 2. Per-candidate findings

### A. RetroBSD/DiscoBSD `cc` toolchain (`ccom`/`cpp`/`as`/`ld`)

This toolchain is a **PCC (Portable C Compiler) derivative**, not a from-scratch "smallc." Its source lives at `usr.bin/ccom/` in the DiscoBSD tree, with files `cgram.y`, `pftn.c`, `trees.c`, `scan.l`, `optim.c`, `gcc_compat.c`, `softfloat.c`, `stabs.c`, and a middle-end directory `mip/` -- confirmed by directory listing at [chettrick/discobsd usr.bin/ccom](https://github.com/chettrick/discobsd/tree/master/usr.bin/ccom).

1. **Language coverage**: inferred (not a directly cited spec) from the presence of `gcc_compat.c` (GNU-extension compatibility shims) and `stabs.c` (debug symbol tables) to be an ANSI/C89-class front end with structs, software floating point (`softfloat.c`, notable since the RP2040 core itself has no FPU), and longs -- fuller than a stripped K&R subset.
2. **Compiler binary size**: not found. No published figure exists in the repo's Makefiles, README, or the RetroBSD wiki.
3. **RAM/heap to compile a ~200-line file**: not found, for the same reason. Measuring this would require building `ccom` and running it, which is outside this research pass.
4. **Thumb-1/ARMv6-M backend**: `usr.bin/ccom` already contains **two** machine-description subdirectories -- `arch-mips` (PIC32/MIPS32r2) and **`arch-arm`** (`code.c`, `local.c`, `local2.c`, `macdefs.h`, `order.c`, `table.c`), confirmed by listing [chettrick/discobsd usr.bin/ccom/arch-arm](https://github.com/chettrick/discobsd/tree/master/usr.bin/ccom/arch-arm). Fetching `arch-arm/macdefs.h` shows it targets **generic 32-bit ARM** -- 16 general registers including R13/SP, R14/LR, R15/PC, 8 FP registers for FPA/VFP, and instruction-encoding assumptions (`FEATURE_HALFWORDS`, `FEATURE_EXTEND`) that presume a full ARM/Thumb-2-class core, not the 16-bit-only Thumb-1 encoding and 8-register model of Cortex-M0+. Fetching `usr.bin/ccom/Makefile` shows `ARCHDIR = arch-mips` and `-Dmach_mips` -- **the ARM backend exists in source but is not wired into the build or shipped in the current image.** Porting to ARMv6-M means writing a new `arch-armv6m` machine description (register allocator in `local2.c`/`table.c`, instruction selection in `code.c`/`order.c`), reusing the PCC middle end but not the existing `arch-arm` files wholesale.
5. **Output format**: assembly text, consumed by the existing native `usr/bin/as`, consistent with PCC's traditional design (not independently re-confirmed for this exact tree in this pass, but standard for PCC-family compilers and consistent with `as`/`ld` being separate binaries in the same `usr.bin` tree).
6. **License**: BSD-3-Clause, per the [chettrick/discobsd](https://github.com/chettrick/discobsd) repository.
7. **Maintenance status**: actively maintained. Latest commit **2026-08-12** ("Time for DiscoBSD 2.7 release"), with releases 2.1 through 2.7 spanning August 2023 to August 2026, per [chettrick/discobsd releases](https://github.com/chettrick/discobsd/releases).
8. **No-MMU/low-memory port precedent**: strong. DiscoBSD self-hosts the full toolchain (`cc`, `as`, `ld`, `make`) on-device today on PIC32 (128 KB RAM, no MMU) and on STM32F4 (Cortex-M4, no MMU), per the repository's own description at [chettrick/discobsd](https://github.com/chettrick/discobsd). The Cortex-M4 target has hardware integer divide and Thumb-2, and more RAM headroom than the RP2040's Cortex-M0+, so it demonstrates the PCC middle end scales to ARM Cortex-M generally but does not itself prove Thumb-1/no-divide fitness.

### B. lcc (Fraser and Hanson, "little C compiler")

1. **Language coverage**: C89/ANSI C, stated directly by the project: "lcc is a retargetable compiler for ANSI C" ([drh.github.io/lcc](https://drh.github.io/lcc/)).
2. **Compiler binary size**: not found in the README, COPYRIGHT, or docs pages. Total source size is reported by secondary sources (not independently verified by line count in this pass) at roughly 20,000 lines.
3. **RAM/heap to compile a ~200-line file**: not found.
4. **Thumb-1/ARMv6-M backend**: lcc's code generators are `.md` (machine-description) files consumed by the `lburg` BURG-style code-generator generator, not one C file per target. Upstream at [github.com/drh/lcc src/](https://github.com/drh/lcc/tree/master/src) has `alpha.md`, `mips.md`, `sparc.md`, `x86.md`, `x86linux.md` -- **no ARM or Thumb `.md` file exists upstream.** Writing a Thumb-1 `.md` file (register classes, instruction costs, divide-emulation calls) is lcc's designed extension point, so it is a bounded, well-precedented task in principle, though nobody has published one for Thumb-1.
5. **Output format**: assembly text for the target assembler (consistent with lcc's traditional design as a retargetable compiler emitting target-specific assembly, not independently re-verified in this pass beyond the `.md`-driven architecture).
6. **License**: not a standard OSI/SPDX-compatible permissive license. Multiple sources (the repository's own COPYRIGHT reference, corroborated by lcc's Wikipedia entry) describe a source-available term prohibiting sale of derived products -- "products derived from LCC may not be sold." No SPDX identifier applies cleanly; this is materially more restrictive than BSD or MIT.
7. **Maintenance status**: dormant. Last commit **2024-10-06** ("Update cwf's home page URL"), per the GitHub commit history at [github.com/drh/lcc](https://github.com/drh/lcc) -- maintenance-only, no active development.
8. **No-MMU/low-memory port precedent**: none found for upstream lcc.

**lcc as already present in the DiscoBSD tree** (`usr.bin/lccom`/`lcpp`): confirmed via directory listing at [chettrick/discobsd usr.bin/lccom](https://github.com/chettrick/discobsd/tree/master/usr.bin/lccom) to carry the same upstream `.md` files (`alpha.md`, `mips.md`, `sparc.md`, `x86.md`, `x86linux.md`) plus `CPYRIGHT`, `LOG`, and `lburg/`. **No `arm.md` exists in this copy either** -- unlike `ccom`, which has a (unused) ARM backend, DiscoBSD's lcc copy has none at all. The `Makefile` evidence for `ccom` (point 4 above) shows `cc` maps to `ccom`/PCC as the primary compiler; `lcc`/`lccom`/`lcpp` are present as a secondary, additional toolchain, not the default.

### C. Smaller C (smlrc)

1. **Language coverage**: "most of the C language common between C89/ANSI C and C99 (minus some C89 and plus some C99 features)," per the project [README](https://github.com/alexfru/SmallerC).
2. **Compiler binary size**: not found in the README or docs.
3. **RAM/heap to compile a ~200-line file**: not found.
4. **Thumb-1/ARMv6-M backend**: **none exists.** The compiler driver documentation states plainly, "The compiler is exclusively an x86/x86-32 toolchain with no support for ARM-based architectures" ([smlrcc.md](https://github.com/alexfru/SmallerC/blob/master/v0100/doc/smlrcc.md)). Its secondary target is MIPS, not ARM, confirmed by the RetroBSD fork's `src/cmd/smlrc/smlrc.c` (BSD-2-Clause, Alexey Frunze, 2012-2016), at [RetroBSD/retrobsd smlrc.c](https://github.com/RetroBSD/retrobsd/blob/master/src/cmd/smlrc/smlrc.c) -- this targets 32-bit MIPS (PIC32MX7, no MMU), not ARM. A DiscoBSD-specific ARM variant of `smlrc` was not found or confirmed in this pass; the smlrc present in the source tree should be assumed MIPS-targeting unless a direct source check of the DiscoBSD tree's `smlrc` directory proves otherwise. Adding a Thumb-1 backend is new codegen work, not a port -- the existing code emits x86 or MIPS assembly text per-target with no ARM scaffolding to extend.
5. **Output format**: assembly text (NASM syntax primarily, with YASM/FASM alternatives on x86; gcc/as-format on the MIPS/RetroBSD fork), then assembled and linked externally -- per the [README](https://github.com/alexfru/SmallerC).
6. **License**: BSD-2-Clause, per the [README](https://github.com/alexfru/SmallerC).
7. **Maintenance status**: actively maintained. Most recent commit **December 22, 2024** ("unhardcode smlrcc invocation"), per the [commit history](https://github.com/alexfru/SmallerC/commits/master).
8. **No-MMU/low-memory port precedent**: strong, but on MIPS, not ARM. The RetroBSD/MIPS fork of smlrc runs on a PIC32MX7 microcontroller with no MMU, and a search-engine summary of the [OSDev Wiki Smaller C page](https://wiki.osdev.org/Smaller_C) (direct fetch returned HTTP 403; this claim is corroborated only by the search snippet, not independently re-verified against the live page in this pass) states the compiler fits into 96 KB of user memory on RetroBSD -- i.e., the exact RAM budget this report targets, just on MIPS rather than ARMv6-M. This is strong indirect evidence that the front end and its memory discipline scale to a 96 KB ceiling; it does not by itself demonstrate anything about Thumb-1 codegen effort.

### D. chibicc

1. **Language coverage**: "almost all mandatory features and most optional features of C11," plus a handful of GCC extensions (preprocessor macros, floats, bit-fields, VLAs, thread-locals), per the [README](https://github.com/rui314/chibicc).
2. **Compiler binary size**: not found.
3. **RAM/heap to compile a ~200-line file**: no number published, but the architecture is a direct red flag for a 96 KB ceiling -- the README states chibicc "allocates all input to memory before tokenizing and never calls `free()`." Memory use grows with source size and is never reclaimed during a compile.
4. **Thumb-1/ARMv6-M backend**: none upstream. chibicc targets x86-64 SystemV only, developed and tested on "Ubuntu 20.04 for x86-64," per the [README](https://github.com/rui314/chibicc). Community forks exist for other architectures, but the ones found -- `chibicc-aarch64` ([xhackerustc/chibicc-aarch64](https://github.com/xhackerustc/chibicc-aarch64)) and `chibicc-arm64` ([ncihnegn/chibicc-arm64](https://github.com/ncihnegn/chibicc-arm64)) -- target **AArch64** (64-bit ARMv8-A application-class cores), the opposite direction from a 32-bit no-MMU Cortex-M0+. No Thumb-1/ARMv6-M port was found. Adding one would mean writing a full new codegen pass plus reworking register allocation and calling convention for Thumb-1's constrained register set and absent hardware divide.
5. **Output format**: not independently confirmed by primary source in this pass; treated as assembly text by architectural convention (consistent with x86-64 SystemV compilers of this style), flagged here as unverified rather than assumed.
6. **License**: MIT, per the [README](https://github.com/rui314/chibicc).
7. **Maintenance status**: not archived, but updates are infrequent; the repository serves partly as the reference implementation for a compiler-writing book, with history dating to at least September 2020 per an [Internet Archive snapshot](https://archive.org/details/github.com-rui314-chibicc_-_2020-10-05_05-33-46). No confirmed recent-commit date was found in this pass.
8. **No-MMU/low-memory port precedent**: none found. All discovered forks move toward larger, MMU-equipped 64-bit ARM targets, not smaller ones.

### E. tcc / TinyCC

1. **Language coverage**: not independently re-verified in this research pass; TCC is broadly documented elsewhere as covering ANSI C plus many GNU C extensions, but that general claim is background knowledge here, not a citation from this pass's fetches.
2. **Compiler binary size**: **approximately 100 KB** for the x86 executable, "including C preprocessor, C compiler, assembler and linker," per the official site ([bellard.org/tcc](https://www.bellard.org/tcc/)). This is a genuinely strong number, though it is the x86 build's size, not a measured ARM/Thumb build's size.
3. **RAM/heap to compile a ~200-line file**: not found. Only qualitative claims exist ("small... footprint," fits on a 1.44 MB floppy), per [tcc-doc.html](https://bellard.org/tcc/tcc-doc.html).
4. **Thumb-1/ARMv6-M backend**: weak to absent. The official docs describe only an "alpha port" for ARM (`arm-tcc`), per [tcc-doc.html](https://bellard.org/tcc/tcc-doc.html). The actively maintained community mob-branch mirror states it "generates machine code for i386, x86_64, arm, aarch64 or riscv64" ([TinyCC/tinycc README](https://github.com/TinyCC/tinycc)), i.e., ARM support has matured past alpha in that fork, but **no stock Thumb-1 support exists in either**. The one Thumb implementation found is a third-party, self-described incomplete fork -- [gfwilliams/tinycc](https://github.com/gfwilliams/tinycc) -- whose own author calls it "a very old piece of work which only works very minimally," targeting **Cortex-M3 (ARMv7-M/Thumb-2)**, not Cortex-M0+/ARMv6-M/Thumb-1, with a hacked-up prologue/epilogue that "only works with very basic stuff (no stack pushing)" and unreliable conditional branches from Thumb's narrow branch-offset encoding. The instruction sets differ (Thumb-2 vs. Thumb-1-only), so this fork is not a direct base for RP2040 work.
5. **Output format**: native machine code directly -- "compile and execute C source directly. No linking or assembly necessary," per [bellard.org/tcc](https://www.bellard.org/tcc/). TCC is the only candidate researched here that bypasses `usr/bin/as` entirely.
6. **License**: LGPL-2.1, per [bellard.org/tcc](https://www.bellard.org/tcc/) and [TinyCC/tinycc README](https://github.com/TinyCC/tinycc).
7. **Maintenance status**: the original author states plainly, "I am no longer working on TCC. Check the mailing list to get up to date information" ([bellard.org/tcc](https://www.bellard.org/tcc/)). Community continuation is active on the mob branch (thousands of commits, mirrored at TinyCC/tinycc and repo.or.cz), so the project is not abandoned, but it is no longer personally maintained by its creator.
8. **No-MMU/low-memory port precedent**: the gfwilliams Cortex-M3 fork is the closest hit and is explicitly a no-MMU-microcontroller target, but it targets the wrong ARM profile (ARMv7-M/Thumb-2, which has more and wider instruction encodings than ARMv6-M/Thumb-1) and is self-described as barely functional. No ARMv6-M-specific or Thumb-1-only port was found.

### F. cproc + QBE

1. **Language coverage** (cproc): "implements most of C11 as well as many C23 features," with enough GNU-extension support to build itself, mcpp, gcc 4.7, and binutils, per the [cproc README](https://github.com/michaelforney/cproc).
2. **Compiler binary size**: not found for either cproc or QBE.
3. **RAM/heap to compile a ~200-line file**: not found for either.
4. **Thumb-1/ARMv6-M backend**: QBE targets **amd64 (Linux/macOS), arm64/aarch64, and riscv64 only -- all 64-bit architectures**, per the [QBE homepage](https://c9x.me/compile/). No 32-bit or Thumb backend exists today, and none was found planned or in progress. QBE's own stated design goal is "70% of the performance of industrial optimizing compilers in 10% of the code," with per-architecture code organized in `amd64/`, `arm64/`, `rv64/` directories -- a Thumb-1 backend would be an unprecedented, from-scratch addition. QBE's intermediate language and register allocator assume a reasonably orthogonal register file and 64-bit words/pointers throughout, a poor structural match for ARMv6-M's 8 usable Thumb-1 registers, 16-bit-only instruction words, and 32-bit (not 64-bit) pointers -- this assessment is an inference from QBE's documented architecture, not a cited statement that a port is infeasible.
5. **Output format**: cproc emits QBE's textual SSA-based intermediate language (IL), not assembly directly, per the [cproc man page](https://github.com/michaelforney/cproc/blob/master/cproc.1) -- QBE itself then emits target assembly.
6. **License**: cproc is ISC; QBE is MIT (Quentin Carbonneaux, 2015-2017), per [qbe LICENSE](https://github.com/8l/qbe/blob/master/LICENSE).
7. **Maintenance status**: both actively maintained, with cproc showing hundreds of commits and CI on builds.sr.ht.
8. **No-MMU/low-memory port precedent**: none. Both tools are cross-compiler-pattern components: cproc is written in standard C99 and needs a C99 host compiler to build; the pairing is designed to run on a full development host and target other machines, not to run compiling itself on a 96 KB-RAM, no-MMU target. Retargeting QBE to Thumb-1 and then somehow fitting cproc+QBE themselves into 96 KB are two separate, both-unscoped, both-undemonstrated efforts.

### G. Small-C lineage (Ron Cain / James Hendrix, and descendants)

1. **Origin and coverage**: Ron Cain published "A Small C Compiler for the 8080s" in Dr. Dobb's Journal issue 45, May 1980, with source released into the public domain and bootstrapped on a PDP-11/45 Unix account, per [Dr. Dobb's: Porting Small-C](https://www.drdobbs.com/web-development/porting-small-c/184405595) and [Wikipedia: Small-C](https://en.wikipedia.org/wiki/Small-C). James E. Hendrix extended it and documented it in *The Small-C Handbook*, forming a major branch of the lineage. The dialect is deliberately a small subset of C (originally no floats, limited types), designed explicitly for 8080/Z80-class microcomputers with very limited memory.
2. **Compiler binary size / RAM to compile**: not found for the original 1980 compiler; period-accurate footprint numbers were not located in this pass.
3. **Thumb-1/ARMv6-M backend**: none in the original. The most relevant living descendant with ARM/MIPS backends is Smaller C (candidate C above), which has MIPS but not ARM.
4. **Output format**: assembly text, consistent with the era's toolchains (background knowledge, not independently re-verified here).
5. **License**: public domain for the original Ron Cain source, per [Wikipedia: Small-C](https://en.wikipedia.org/wiki/Small-C). Descendants carry their own licenses (see Smaller C above, BSD-2-Clause).
6. **Maintenance status**: the original is historical, not maintained; only living descendants matter for this report.
7. **No-MMU/low-memory port precedent**: this is the whole point of the Small-C lineage's design -- it targeted tens-of-KB 8-bit micros by design, decades before "embedded" was a distinct engineering category. The strongest living link to today's 96 KB target is Smaller C's confirmed 96 KB RetroBSD/MIPS deployment (see candidate C, point 8).
8. Other descendants found by name only, not independently verified in this pass: **PhrozenC**, described in search results as a K&R-C, Small-C-derived compiler targeting the Amstrad CPC (Z80) that runs natively from ROM/cartridge -- flagged as a lead, not a confirmed primary-source fact.

### H. cc65

1. **Language coverage**: characterized in search results (not independently confirmed against a primary cc65 doc page in this pass) as descending from a Small-C-family compiler adapted for the Atari 8-bit by John R. Dunning, now "mostly ANSI compliant."
2. **Compiler binary size / RAM to compile**: not found.
3. **Thumb-1/ARMv6-M backend**: cc65 targets the 6502, an 8-bit CPU with a tiny register set (essentially one 8-bit accumulator and two 8-bit index registers) and weak addressing modes. Sources describe its backend as forced into stack/accumulator-centric code generation by that register model, and note explicitly that it "doesn't fully take advantage of the 6502 when performing 8-bit operations" -- i.e., cc65's own generator is known to leave performance on the table even on its native target, which is a caution against treating its architecture as a clean template. No evidence was found of anyone porting cc65's front end or backend design to ARM or another tiny 32-bit target. The only adjacent modern project is llvm-mos, a from-scratch LLVM backend for 6502, unrelated to cc65's own code.
4. **Output format**: assembly text for the ca65 assembler (background knowledge about cc65's toolchain structure, not independently re-verified by primary-source fetch in this pass).
5. **License**: zlib, per [cc65/cc65](https://github.com/cc65/cc65).
6. **Maintenance status**: active (thousands of GitHub stars, ongoing snapshot builds); exact last-commit date not captured in this pass.
7. **No-MMU/low-memory port precedent**: cc65's own native target (6502 home computers, kilobytes of RAM) is itself a no-MMU, very-low-memory precedent, but that is a statement about the 6502 target, not about any ARM port -- none exists.

### I. c4 family (including AMaCC and pshell)

1. **c4 itself** ([rswier/c4](https://github.com/rswier/c4)): GPL-2.0, roughly 500 lines across four functions (`next`, `expr`, `stmt`, `main`), self-hosting. Confirmed missing, by direct source inspection: `float`/`double`, `struct`/`union`, `switch`, `for`/`do-while` (only `while` exists), `break`/`continue`, a real preprocessor (only comment-like `#` handling), and general casts; function parameters are effectively `int`/`char` only. It supports `char`/`int`/pointers, `if`/`while`/`return`, arithmetic/logical/bitwise/comparison/assignment operators, array indexing, enums, and a small hardcoded set of library calls. Critically, the original c4 is a **bytecode interpreter/VM**, not a native-code compiler -- it self-compiles into and executes from an internal VM, never emitting machine code. Given the missing struct/union/switch support, c4 by itself is a teaching toy, not a realistic bootstrap compiler for real embedded C source, which routinely uses structs.

2. **AMaCC** ("Another Mini ARM C Compiler," [jserv/amacc](https://github.com/jserv/amacc)): a c4-lineage parser extended to emit real ARM machine code, roughly 2,366 lines. Coverage is materially broader than c4 -- all C89 statements except `typedef`, all C89 expression operators, char/int/enum/struct/union types, multi-level pointers. License is GPL-2.0-family (exact "-only" vs. "-or-later" not disambiguated in this research pass; check [amacc/LICENSE](https://github.com/jserv/amacc/blob/master/LICENSE) directly). Its target is **armv7hf**: 32-bit ARM, hard-float ABI, Linux userspace, verified on Raspberry Pi 2/3/4 -- not Cortex-M0+/Thumb-1/ARMv6-M, and it assumes a Linux ELF/MMU environment, so it needs substantial rework for bare-metal RP2040 use. Measured on a Raspberry Pi 4B: a **100 KiB** binary, 0.0217-second compile time for its test input, and roughly 70 percent of `gcc -O0` runtime performance, per the project's own README.

3. **pshell** ([lurk101/pshell](https://github.com/lurk101/pshell)) -- the strongest concrete finding in this entire research pass. This is a self-hosted shell, filesystem, `vi` editor, and **C compiler that runs natively on the RP2040 (Cortex-M0+) and RP2350 (Cortex-M33) themselves**, i.e., an existing, working, shipping example of exactly the "compile on the embedded device" capability this report is evaluating, described further in a [Hackaday article](https://hackaday.com/2022/08/01/self-hosted-pi-pico-development/). Its lineage is explicitly documented as a remix of the AMaCC parser and the c4 virtual machine, with floating-point, array, struct, and type-checking enhancements drawn from the Squint project, and **native Thumb code generation for Cortex-M0+/M33 added by Jean M. Cyr** -- actual native Thumb machine-code emission on-device, not JIT-to-VM interpretation.
   - **Language coverage**: int/float/char/pointer types, arrays up to 3 dimensions, struct, union, for/while/if-else/break/continue/switch/goto -- materially fuller than either c4 or AMaCC alone, and closer to a usable C subset for real embedded code.
   - **License**: GPL-2.0, per the repository's LICENSE file.
   - **Memory evidence**: a status output example in the project shows "heap: 461.5K, program code space: 16K, global data space: 16K" on a Pico2 (RP2350, which has substantially more RAM than the RP2040). A precise RP2040-specific figure was not captured in this research pass and would need a follow-up fetch of the repository's RP2040-specific numbers to confirm a fit within the 96 KB per-process ceiling described in this report; treat the Pico2 figure as an upper-bound reference point, not a direct RP2040 measurement.
   - **Maintenance status**: active, 600-plus commits, current version 2.1.5 at time of research, with an ongoing discussion thread in the project about Thumb-1 instruction-generation optimization -- most Thumb-1 instructions are 16-bit, which the maintainers cite as an active complexity in their own code generator. This is a live, primary-source confirmation that native Thumb-1 codegen from C source is being actively engineered today on this exact class of hardware.
   - **Output format**: native machine code directly (Thumb instructions written into RAM/flash for execution), not assembly text -- it does not go through `usr/bin/as`.

Also surfaced but not independently verified in this pass, flagged as leads only: **CC500** ([8l/cc500](https://github.com/8l/cc500), described as "a tiny self-hosting C compiler") and **andrewchambers/c** ([andrewchambers/c](https://github.com/andrewchambers/c), described as a "small self hosting C compiler"). Neither was fetched and read directly; both would need primary-source verification before being treated as real candidates.

### J. picoc (assessed explicitly as an interpreter, not a compiler)

1. **Nature**: a tree-walking interpreter. It re-parses and re-interprets source on every run and produces no persistent object or executable code -- fundamentally a different tool category from every compiler discussed above.
2. **Canonical location**: the GitHub repository [zsaleeba/picoc](https://github.com/zsaleeba/picoc) is now a stub redirect; the maintained upstream is [gitlab.com/zsaleeba/picoc](https://gitlab.com/zsaleeba/picoc).
3. **Language coverage**: a restricted C subset, per the project's own README text (confirmed via a fork mirror, [jpoirier/picoc README](https://github.com/jpoirier/picoc/blob/master/README.md)): no real preprocessor (only limited `#define`/`#ifdef`), no K&R-style function declarations, **no function pointers**, storage classes (`static`/`extern`/`volatile`/`register`/`auto`) are parsed but semantically ignored, structs/unions are global-scope only, no bitfields, and `goto` is forward-only. The lack of function pointers in particular is a hard blocker for a meaningful amount of real-world embedded C.
4. **Compiler/interpreter binary size**: the core interpreter source is about 3,500 lines, and the compiled interpreter "only takes a few k of code space," per the same README text -- genuinely small.
5. **RAM**: the default interpreter stack size is 512 KB, configurable via a `STACKSIZE` build setting, per the same README -- as shipped by default this is far above the 96 KB per-process ceiling and would need to be reduced and tested, not assumed to already fit.
6. **License**: BSD (New BSD / BSD-3-Clause-equivalent), per the README and repository LICENSE reference.
7. **Maintenance status**: effectively unmaintained. Both the GitHub mirror's last commit (the 2018-06-05 move-to-GitLab notice) and the GitLab repository's own last commit ("Fixed a minor build issue," also 2018-06-05) show no activity for eight-plus years as of this report's date.
8. **What it buys as a fallback tool**: fast edit-run iteration with no separate compile-then-link-then-load cycle, and a genuinely tiny code footprint, at the cost of (a) producing no reusable compiled artifact, (b) a dialect restricted enough to reject a meaningful amount of real embedded C (no function pointers is the sharpest limitation), and (c) needing its own stack-size tuning against the 96 KB ceiling before any of its "small footprint" framing can be taken as proven for this platform. Because it never emits machine code, "porting picoc to Thumb-1" is really just "does whatever builds it already target Thumb-1" -- a much smaller question than the code-generation porting effort every AOT compiler above requires.

## 4. Ranked shortlist (at most three candidates)

### Rank 1: pshell's native Thumb-1 code generator (c4/AMaCC/Squint lineage)

pshell is the only candidate in this research pass that already compiles C to native Thumb machine code and runs that compiler natively on an RP2040-class Cortex-M0+ device today, per [lurk101/pshell](https://github.com/lurk101/pshell) and the [Hackaday coverage](https://hackaday.com/2022/08/01/self-hosted-pi-pico-development/). This resolves the two hardest open questions this report asked of every other candidate -- "does a Thumb-1 backend exist" and "does it fit on this class of hardware" -- with a working, maintained answer rather than an estimate. Its GPL-2.0 license and c4/AMaCC lineage mean its C dialect is a practical subset (int/float/char/pointer/array/struct/union/switch/goto) rather than full C99, which matches this platform's own 2.11BSD libc (itself a POSIX subset) reasonably well.

Port-effort steps:
- Fetch and read pshell's RP2040-specific (not just Pico2/RP2350) memory-usage numbers directly from its README and source to confirm heap, program-code-space, and global-data-space figures fit inside the 96 KB MAXMEM ceiling on the smaller-RAM RP2040, since only a Pico2/RP2350 example was captured in this pass.
- Extract pshell's parser, code generator, and runtime library from its own shell/filesystem harness, and adapt it to emit a.out format objects (or hand the assembly path to `usr/bin/as` if pshell's native-codegen approach can be redirected to produce assembly text instead of direct machine code) so its output integrates with DiscoBSD's existing `usr/bin/ld` and process-loading path.
- Cross-check pshell's struct/union/switch implementation against 2.11BSD libc's header usage (structs used throughout `<sys/*.h>`) to confirm its "struct, union" support is complete enough to compile real system headers, not just self-contained test programs.
- Package pshell's compiler as a standalone `usr/bin/cc`-family binary sized against the 340-720 KB flash budget, since as an interpreter-plus-compiler-plus-shell bundle it may currently include shell and filesystem code the DiscoBSD image does not need duplicated.

### Rank 2: DiscoBSD's own `ccom` (PCC), given a new ARMv6-M backend

`ccom` is already the system's default, shipping, actively maintained compiler, already self-hosts on other no-MMU/low-RAM ARM and MIPS targets, and already contains a full PCC middle end plus a (currently unused, wrong-ISA) ARM backend directory to use as a structural reference, per [chettrick/discobsd](https://github.com/chettrick/discobsd). Because `cc` already maps to `ccom` today, a successful ARMv6-M port would let DiscoBSD self-host its actual primary compiler on the actual RP2040, rather than depending on a secondary or replacement tool. Its BSD-3-Clause license and August 2026 last-commit date are the best license and maintenance combination of any candidate researched. The open risk is that no primary source gives a binary-size or compile-time-RAM figure for `ccom` today, so its fit within 96 KB is unverified and must be measured directly, not assumed from the PIC32/STM32F4 precedent.

Port-effort steps:
- Build `ccom` for the existing `arch-mips` target and measure its own binary size and peak RSS while compiling a representative 200-line C file, to establish a real baseline before investing in a new backend, since no such number exists anywhere in the primary sources checked.
- Write a new `arch-armv6m` machine description under `usr.bin/ccom/`, deriving register classes and instruction selection in `code.c`/`order.c`/`table.c` from `arch-arm`'s structure but restricting register allocation to Thumb-1's 8 generally usable registers, replacing every 32-bit-ARM-only instruction pattern (`arch-arm`'s FPA/VFP assumptions in particular) with software-floating-point calls via `softfloat.c`, which the tree already carries.
- Add software integer-divide emulation calls in the new backend's instruction selection, since ARMv6-M has no hardware divide and `arch-arm`'s `macdefs.h` does not appear to already assume one is absent.
- Wire `ARCHDIR = arch-armv6m` into a new build configuration alongside the existing `arch-mips` default, and cross-build a test image before touching the default `cc` target, so the working MIPS/PIC32 path is not disturbed during bring-up.

### Rank 3: Smaller C (smlrc), ported from its MIPS backend to ARMv6-M

Smaller C is the strongest fallback if `ccom`'s PCC middle end proves too heavy once actually measured (point 2 in Rank 2's risk list): it has a demonstrated, cited 96 KB-class deployment on RetroBSD/MIPS today (candidate C, point 8), a permissive BSD-2-Clause license, and active maintenance as of December 2024, per the [commit history](https://github.com/alexfru/SmallerC/commits/master). Its C89/C99-hybrid dialect is smaller and more tractable to retarget than PCC's fuller ANSI-plus-GNU-extensions surface, and its existing MIPS backend (in the RetroBSD fork) is a concrete, readable template for how its code generator structures per-target assembly emission, unlike lcc's `.md`/BURG approach or QBE's 64-bit-only IL. It ranks below `ccom` only because it would mean maintaining a second, non-default compiler in the tree rather than fixing the one DiscoBSD already ships as `cc`, and below pshell because it starts from zero working Thumb-1 output rather than an existing one.

Port-effort steps:
- Read the RetroBSD fork's `src/cmd/smlrc/smlrc.c` MIPS assembly-emission routines directly, since this is the closest existing analog to the low-memory target this report cares about, and use it as the template for a new ARM emission module rather than starting from the x86 NASM-output code path.
- Write a new Thumb-1 assembly-emission back end that reuses Smaller C's existing intermediate representation and register-allocation logic, restricting output to the 16-bit narrow Thumb-1 encodings and replacing MIPS-specific division/multiplication instruction emission with calls to a software divide routine.
- Retarget the compiler driver (documented in [smlrcc.md](https://github.com/alexfru/SmallerC/blob/master/v0100/doc/smlrcc.md)) to invoke `usr/bin/as` and `usr/bin/ld` instead of the x86/MIPS toolchains it currently drives, so its assembly-text output integrates directly with DiscoBSD's existing native assembler and linker.
- Verify a 96 KB-class RAM fit directly on RP2040 hardware by building the retargeted compiler and measuring peak heap while compiling a representative 200-line file, rather than relying on the unverified OSDev Wiki summary of its MIPS-target RetroBSD footprint as a stand-in for the ARM case.

None of the remaining candidates rank in the top three. tcc and cproc/QBE are ruled out primarily by their commitment to architectures and IR designs (64-bit words, richer register files) structurally distant from an 8-register, 16-bit-instruction, no-divide core, not by any demonstrated multi-hundred-KB or 1 MB-plus footprint -- no candidate in this research pass was found to actually carry such a footprint, which is itself a gap: several compilers (chibicc, cproc, QBE, lcc, `ccom`) simply have no published binary-size or compile-time-RAM number at all, and that absence should not be read as a quiet pass.
