# i86: a real-mode PC for DOS in a user process

`usr.bin/i86` (manual page `i86.1`) runs PC DOS systems on an emulated Intel
8086, 80186 or 80286 in real mode. It is an ordinary program: it needs no
kernel option, lives in the 192 KB process window with every other program,
and takes its disks, its page file and its terminal from the file system
and the tty it is started on. This document is the authority for its
design, its measured costs and the evidence each claim has. Proposals and
work not yet built are in `docs/research/i86-dos-emulator.md`.

## Structure

| File | Role |
| --- | --- |
| `cpu.c`, `i86.h` | the interpreter: one call executes one instruction with its prefixes, or takes a pending interrupt |
| `mem.c`, `mem.h` | guest memory: one megabyte of address space in one-kilobyte pages, a fixed number resident, the rest in a page file |
| `pc.c`, `pc.h` | the machine: firmware services, text display, keyboard, disks, timer, clock, ports |
| `gfx.c`, `gfx.h` | the PicoCalc panel as the display: text cells and the color adapter's graphics modes on `/dev/lcdgfx` |
| `serial.c`, `serial.h` | COM1, an 8250 UART with a Microsoft serial mouse on its lines |
| `ems.c`, `ems.h`, `dos/ems.asm` | expanded memory: the LIM EMS 4.0 services of interrupt 67h over the pager's logical pages, and EMS.SYS, the DOS driver that names them |
| `font.h`, `font/` | the two code page 437 fonts of the panel display, generated by `font/mkfont.py` from subsets of the public-domain Misc-Fixed 4x6 and 5x8 fonts, with the sixteen pictures the 4x6 font lacks drawn by the generator |
| `main.c` | options, the step loop, the host terminal, the one exit path |

### Memory

The guest's 640 KB cannot be resident in a 192 KB window, so `mem.c` pages
it. Two tables indexed by page hold, for each page, the address of its
resident copy minus the page's guest address; an access adds the guest
address and loads, and a zero entry calls the pager. A resident page absent
from the read table has not been referenced since the clock hand passed,
and one absent from the write table has not been modified: both conditions
cost a call once, not a store on every access. This is the reference-bit
simulation of the VAX BSD pager applied to an interpreter.

A victim page reaches the page file only when modified and nonzero. A page
with no copy in the file is supplied as zeros. The file is created
exclusively on the first page put aside, at `/tmp/i86.<pid>` unless `-s`
names another path, and its name is removed while it is open: an existing
path is refused, nothing is removed by name afterwards, and the pages go
with the process however it ends.

Page size, measured on the host by booting FreeDOS 1.1 and running `ver`
and `dir` (17.7 million instructions), pages read back from the file:

| Resident | 4 KB pages | 2 KB pages | 1 KB pages |
| --- | --- | --- | --- |
| 32 KB | 108,425 | 74,371 | 27,528 |
| 48 KB | 55,885 | 11,340 | 8,835 |
| 64 KB | 32,662 | 5,460 | 4,332 |
| 96 KB | 1,672 | 1,896 | 837 |
| 128 KB | 592 | 153 | 167 |
| 160 KB | 36 | 29 | 77 |

In bytes read at 96 KB that is 6.7 MB, 3.8 MB and 837 KB, which decided the
one-kilobyte page. The minimal SvarDOS floppy (boot, `dir`, `mem`, `ver`)
reads 98 pages back with 128 resident and 408 with 96. The process window
holds 136 frames beside the program (Renode, PICO_UART kernel: 136
accepted, 144 refused). With the panel display built in, 132 frames were
accepted and 136 refused (Renode, PICOCALC_SD kernel); with COM1 and the
mouse, 131 and 132; with expanded memory, 126 and 127, and with `-e 2048`
124 and 125. The default is 124, which fits both; a larger `-e` needs
a smaller `-f`.

Two more services of the pager exist for the panel display. A window of
sixteen pages outside paged memory can be watched: the first write to
one of its pages takes the slow path once and sets a bit, and
`mem_rearm()` returns the bits and arms the pages again. It is the
modify-bit simulation above, applied to display memory, and it replaces a
second copy of the 16 KB of a graphics mode. And the pager lends frames:
`mem_lend(8)` empties the last eight frames into the page file and
hands their memory over until `mem_return()`. A graphics mode takes its
odd scan lines from that loan, so a text-mode session keeps every frame
and a graphics-mode session pages with eight fewer.

### Machine

No firmware code runs in the guest. Every interrupt vector points at a
four-byte entry in segment F000 holding `0F FF nn`, which the interpreter
recognizes only when fetched from that segment and turns into a call of
`pc_trap(nn)`. The services implemented: 10h (text modes 0-3, with a
request for the monochrome mode 7 answered by mode 3, cursor, scroll, read and write cells, teletype, write string; on the panel display also modes 4, 5 and 6 with the palette, write-pixel and read-pixel functions), 11h, 12h,
13h (reset, status, read, write, verify, parameters, type; two floppies and
two hard disks in image files), 15h (88h, 86h), 16h (read, poll, shift
state), 1Ah (ticks, clock), 19h, and the 18.2 Hz interrupt 8 with its chain
to 1Ch. A blocking key read lets interrupts in while it waits, so the tick
count keeps time. Services 13h, 15h and 16h return with interrupts enabled, as the
IBM firmware does: the SvarDOS kernel times its start-up key wait with
interrupts off and depends on that.

The display is the 4000 bytes of color text memory. A refresh sends the
cells that differ from the last frame as ANSI cursor addressing and SGR
colors; a scroll of the whole screen goes to the terminal as line feeds
inside a 25-line scroll region. Characters outside ASCII are drawn as their
nearest ASCII shape. The PicoCalc console has 53 columns, so on it DOS
runs in the 40-column mode (`-w 40`) or on the panel display below.

A word read or written at a port is two byte accesses, at the port and
the next one, as the PC's bus makes them for its eight-bit devices.

### Mouse

COM1 is an 8250 UART at ports 3F8h to 3FFh on interrupt line 4, named at
40:00 and counted in the equipment word, and on its lines sits a
two-button Microsoft serial mouse, for drivers of Microsoft-compatible
serial mice. CuteMouse is the one run (Evidence status); the serial mouse
driver of Windows 3.0 has not been run, and drivers for bus or PS/2 mice
find nothing. The UART interrupts for received data only, and
only while OUT2 is set, as the PC's serial adapter gates the line; its
transmitter is always empty. The mouse takes its power from RTS: when RTS
rises it sends `M`, and it reports a movement and the buttons in three
bytes. The bytes reach the receive register 8 ms apart, the byte time of
its 1200 bit/s, and each waits there until the guest reads it, so a
report is never split. Sixteen reports can be on their way; one that does
not fit is dropped, and its buttons are sent again as soon as a report
fits, so no button stays down in the guest. The behavior follows 86Box's `serial.c` and
`mouse_serial.c` and the protocol notes of CuteMouse.

The PicoCalc has no pointing device, so its keys move the mouse.
Control-\\ turns mouse keys on and off; while they are on, the panel
shows a white arrow in its top margin and:

| Key | Mouse |
| --- | --- |
| Up, Down, Left, Right | moves 8 mickeys; the same arrow again within six timer ticks (330 ms), as the keyboard repeats a held key every 100 ms, moves twice the last step, up to 64 |
| `[` | clicks the left button |
| `]` | clicks the right button |
| `{` (Shift+`[`) | presses the left button and holds it, for dragging, until `{` or `[` comes again |
| `}` (Shift+`]`) | the same for the right button |

The brackets click because their sides match the buttons' and each is
one unshifted key; the keyboard firmware reports the arrows and the
bracket keys from one group of buttons apart from its key matrix
(`picocalc_keyboard`, `keyboard.ino`). Every other key, Home, End and the
paging keys among them, still types. With mouse keys off the arrows are
cursor keys and the brackets type. At CuteMouse's defaults a tap moves its
text cursor two columns or one row.

### Expanded memory

`-e kbytes` gives the machine that much expanded memory under the Lotus,
Intel and Microsoft Expanded Memory Specification 4.0, from 16 KB to
32 MB; without it interrupt 67h does nothing. Programs find an expanded
memory manager through the DOS device `EMMXXXX0`, so DOS loads
`EMS.SYS` (`dos/ems.asm`, `DEVICE=C:\EMS.SYS`, which `mkdosdisk.sh` puts on
its disks). The driver installs only on i86 with expanded memory, answers
every device request with "done", and points interrupt 67h at the
firmware; 66 bytes of it stay resident.

The pages of expanded memory are the pager's logical pages from 1024 on,
so they cost no RAM until used and go to the page file like conventional
memory (`mem.h`). Each 16 KB physical page shows sixteen consecutive
logical pages; a mapping changes which ones and costs no copy. The
physical pages are the page frame at E000h (pages 0 to 3) and A000h to
B7FFh and C000h to DFFFh, which this machine leaves empty: 288 KB above
640 KB, the space Windows 3.0 in real mode banks applications into
(Microsoft, *Windows Guide to Programming* 3.0, section 16.1.2). No
conventional memory is mappable and handle 0 owns no pages: Windows would
otherwise shrink handle 0 and map its pages below 640 KB, over memory
where EDR-DOS keeps its own data.

All functions of version 4.0 are served except 55h and 56h (alter the map
and jump or call), which answer 84h. There are no hardware alternate map
register sets, so function 5Bh simulates set 0 as the specification's
Appendix D has an operating environment do: the save area 5B01h makes
current stands for the registers, a switch stores the mapping in the area
left, and 5B00h stores the mapping in the current area before it returns
its address. Windows 3.0 switches tasks this way. There are no DMA register
sets: 5B06h and 5B07h answer 9Eh. Function 5Dh keeps the operating
system's access key, handing it out on the first 5D00h or 5D01h,
taking it back with 5D02h (A4h when none is out) and refusing 5900h and
5Bh with A4h while the functions are off. A move
(57h) between conventional memory and a handle's pages that a physical
page shows at the conventional address answers 94h; a partial map (4F00h,
4F01h) with more entries than physical pages answers A3h, and 4F01h
checks every entry before it applies one; every buffer address wraps at
1 MB. Status codes follow the specification's Appendix A.

### Panel display

With `-g` the display is the PicoCalc's panel through `/dev/lcdgfx`
(`sys/lcdgfx.h`), which the PICOCALC and PICOCALC_SD kernels have, and
the terminal carries only the keys. The adapter's 200 lines occupy panel
lines 60 to 259.

- Text: a cell is 8 pixels high and 4 wide at 80 columns, 8 wide at 40,
  so both widths fill the panel's 320 pixels. All 256 characters of code
  page 437 are drawn in the sixteen colors, the line and block characters
  computed so that they meet across cells; the cursor is the cell's two
  bottom lines. Changed cells go out as one-bit windows, one for each run
  of one attribute in a row.
- Modes 4 and 5 (320 by 200, four colors) map one to one. The palette
  follows the color register and function 0Bh.
- A mode set clears all 16 KB. One that asks for memory to be kept (bit
  7 of the mode) keeps all of it between graphics modes; between a text
  and a graphics mode only the cells' 4 KB exist on both sides, and the
  other 12 KB read as zeros on entering the graphics mode.
- Mode 6 has 640 pixels a line where the panel has 320. Each pair becomes
  one pixel of three levels (neither, one or both set), so a line one
  pixel wide stays visible at half brightness.
- The firmware's characters, scrolling and pixels in a graphics mode
  write display memory, as do programs; the mode register at 3D8h
  switches between cells and pixels for a program that sets the adapter
  itself.

The first 128 characters of the 8-pixel font are also the firmware's
character table at F000:FA6E, where programs that draw their own text
read it.

A program that holds the pixel device silences the console
(`sys/lcdgfx.h`), so the Control-] menu closes the device, shows its
line on the console and opens the device again; the exit paths close it
before they print. If the device is absent (PICOCALC_LEAN, PICO, the
host) or cannot be opened again, the terminal is the display, which has
no graphics mode: mode numbers 4 to 6 then select 80 columns of text, as
they do without `-g`.

Interrupts come through an interrupt controller at ports 20h and 21h:
request, in-service and mask registers, fixed priority, the specific and
non-specific end-of-interrupt commands, and the initialization sequence
with its vector base and its automatic end of interrupt.
The timer is on line 0 and the keyboard on line 1.

The timer is an 8254 at ports 40h to 43h counting 1,193,182 clocks a
second: control words, counter latches and the read-back command; read and
load of the low byte, the high byte or both; modes 0, 2 and 3 counted (1, 4
and 5 count as mode 0, with no gate trigger; BCD counts four decimal
digits). Counter 0 raises line 0 at each period of its count, 65536
(18.2 Hz) until the guest loads another, the first at the first poll as
the firmware's tick came; counter 2's gate is bit 0 of port 61h (its rise
restarts modes 2 and 3) and its output bit 5, mode 2's one-clock low pulse
showing to the first read after it, and bit 4 toggles every 18 clocks as
the refresh request does. A count loaded while counting takes effect at
once. Time is the host's clock at each poll and, between polls, the
instructions run times the clocks an instruction took over the last
running stretch, so a counter moves between two reads and never runs
backwards; a step back of the host's clock leaves the counters where they were. Under `-T` a poll
is 5 ms and 5,966 clocks, so a guest that keeps the 18.2 Hz rate sees its
interrupts at the polls it saw before the 8254 existed (the earlier
tests' poll counts are unchanged). Only a timer faster than a poll
shortens a run of instructions, to the time left before its interrupt,
including a count loaded during the run, and a guest halted under such a
timer moves time to its next interrupt rather than a poll; at most four
interrupts wait. Windows 3.00a, Word 1.1 and Excel 2.1d never read the
counters; they write port 61h from their keyboard handler and program
counter 2 once for a beep (`i86-dos-emulator/office10-host.txt`).

`-S mhz` keeps the guest to the speed of the processor `-c` names at that
clock: after each run of instructions the emulator sleeps until the host's
clock catches up with the instructions' time at 13.1 (8088), 9.9 (8086),
7.7 (80186) or 5.2 (80286) clocks each, the figures of one loop that
`docs/research/i86-dos-emulator/cpu-timing.md` derives from Intel's
manuals and checks against silicon. A guest behind its pace keeps at most
20 ms of credit, so on a board slower than the clock asked for `-S` leaves
the speed as it was; `-v` prints the rate reached and the rate aimed at.

Keys are the terminal's bytes turned back into key presses. Each becomes
scan bytes at port 60h with one interrupt 9 apiece: the modifiers the
character needs, the key's make byte, its break byte, the modifiers
released. The handler behind vector 9 keeps the shift flags at 40:17 and
puts the key code into the buffer at 40:1E, which interrupt 16h reads; a
guest that takes vector 9 sees the scan bytes first. A terminal reports no
key releases, so no key is ever seen held.

An invalid opcode on the 80186 or 80286 that reaches the firmware's own
vector 6 ends the session with the instruction's address and status 4. The
firmware of a real machine returns, which runs the instruction again
without end; a 386 boot sector on the 80286 model is the usual cause.

Control-] on a drawn display opens a menu: leave, or put another image in
a floppy drive while the guest runs. The drives report no change line
(13h AH=15h answers 1), so DOS reads a disk's parameters again after two
seconds without access and needs no signal from the drive.

What three DOS systems ask of the firmware that it does not implement, from
a host build with `-DI86_TRACE` (80286 model; boot, `dir`, `ver` or `mem`):

| System | Unimplemented calls made | Vectors the system takes over |
| --- | --- | --- |
| FreeDOS 1.1 | 10h AH=01 (cursor shape), 10h AH=12 (EGA information), 1Ah AH=03 and 05 (set clock) | 8, 9 |
| MS-DOS 5.0 | 10h AH=01, 15h AH=C0 and 41, 16h AH=92, keyboard controller commands on port 60h | 8, 9, 13h, 15h |
| SvarDOS 20250427 | 10h AH=01, 15h AH=E8 and 41, 16h AH=03 | 13h |

None of these stops the systems. The handlers FreeDOS and MS-DOS install
on interrupt 9 receive the scan bytes and chain to the firmware's.

## Cost

Target build, arm-none-eabi-gcc 16.2.0: text 42,336, data 408, bss 20,908
bytes (42,228, 408 and 20,716 before the single read of each guest array
in `ems.c`; 37,480, 404 and 20,508 before expanded memory; 36,316, 396 and
20,400 before COM1 and the mouse; 29,624 and 20,792 before the panel display, of whose 6.6 KB the
two fonts are 3 KB; 27,200 and 20,436 before the interrupt controller, the
keyboard interrupt and the disk menu); `cpu.c` is compiled at `-O2` and
the rest at `-Os`.

The panel display's cost on the wire is not measured. A full graphics
frame is 64,000 pixels of two bytes; a refresh runs at most once a timer
tick, 18.2 times a second, and sends the lines of the pages written since
the last one, about thirteen lines for each kilobyte of a field.

Thumb instructions executed for each step of the interpreter, counted
under `qemu-arm -cpu cortex-m0` by the plugin of
`docs/research/i86-dos-emulator/measure` over 12 million steps of a
FreeDOS session (boot, then `dir`, `ver`, `type`). A step is one guest
instruction, with two exceptions: a repeated string instruction runs up to
256 iterations in one step, and a step may only deliver an interrupt.

| Build of the interpreter | Thumb instructions per step | `cpu.o` text |
| --- | --- | --- |
| first version, `-Os` | 211 | 7,184 |
| one dense switch, one event word, `-Os` | 181 | 7,184 |
| inlined fetch, `-Os` | 173 | 7,996 |
| the same at `-O2` | 161 | 10,808 |
| repeated instructions bounded at 256 iterations a step (shipped) | 163 | not re-measured |

In the shipped build's run, 46,910 of the 12,000,000 steps were repeated
string instructions and carried 824,104 iterations, so the 1,950,300,339
Thumb instructions spread over 12,777,194 instructions and iterations, 153
apiece. The four earlier rows were measured with a whole repeated
instruction in one step and their composition was not recorded.

At the RP2040's clock this implies a guest of the order of an IBM PC XT.
A board run of one CPU-bound loop agrees: 0.32 million guest instructions
a second on a bare Pico at 125 MHz, with no display and no paging
(`docs/research/i86-dos-emulator/board-speed-pico.txt`). That loop costs
about 219 Thumb instructions a step under qemu-user, more than the FreeDOS
mix above, and the board time implies about 1.8 cycles per Thumb
instruction across the two builds.

## Limits

- No protected mode on the 80286 model: LMSW stores nothing and SMSW
  reports real mode. Address line 20 is held low, so there is no high
  memory area and no extended memory, and no XMS driver: Windows 3.0 runs
  in real mode only (`win /s` is refused). What standard mode needs is in
  `docs/research/i86-dos-emulator.md`, section 3.
- Expanded memory maps no conventional page: its 18 physical pages lie
  above 640 KB (A000h to DFFFh and the E000h frame). Windows 3.0 reports
  this arrangement as "Large Frame EMS" (`windows30-host.txt`). There are
  no hardware alternate map sets and no functions 55h and 56h; 32 MB at
  most.
- The 80286 model wraps a word at offset FFFFh inside its segment, as the
  8086 does; the 80286 raises interrupt 13 there and interrupt 12 on the
  stack. Two more classes of the 80286 vectors differ: one ENTER vector
  with an odd stack pointer at the top of the segment, and an IDIV
  overflow in 2 of 1,147 vectors where the 80286 stores 80h and does not
  trap. The flags a divide error leaves are not compared on either
  processor.
- Graphics exist on the panel display only and are those of the color
  adapter: no EGA, VGA, Hercules or Tandy mode, one display page, no
  blinking, no cursor in a graphics mode, no border color, and function
  08h reads no character back from pixels. Mode 6 shows half its
  horizontal resolution. A palette change draws the whole frame again.
  The retrace bits of port 3DAh alternate on every read and follow no
  timing.
- No coprocessor, no sound, no parallel port. COM1 carries the mouse and
  nothing else: no COM2, no interrupt 14h service, no transmitter, no
  modem status besides loopback. The mouse has two buttons and no wheel,
  and a button is held only through `{` and `}`, since a terminal
  reports no key release.
- A key is pressed and released in the same instant; a held key cannot be
  represented from a terminal. The keyboard controller accepts no commands
  (LEDs, typematic rate), and extended keys send no E0 prefix.
- Without a PSRAM or a card partition at `/tmp`, the page file is on the
  root file system: on the flash root that is program and erase traffic,
  and a full root ends the session with status 3.
